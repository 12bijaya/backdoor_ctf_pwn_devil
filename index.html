Analysis

This is the elf file of the x86_64 architecture.

First step in the binary exploitation exploiter must takes always must be check the protection for the binary.

Here in this challenge the binary don’t have canary that means we can overwrite the RIP. It doesn’t have PIE which means the offset of the binary addresses will be remains same. And the RELRO is partial relro which means if the binary have the format string vulnerability we can overwrite the got address.

Reversing the binary

Looking for the functions

In the binary the user defined functions in the binary are:

initialize
control_manipulation
bomb_devils_contract
war_devils_prophecy
main

initialize()

The initialize functions contains the variable which contains the address of the system.

control flow

The control flow of the binary is the simple.

first prints the some content and calls the function int he following orders
control_manipulation()-->war_devils_prophecy()-->bomb_devils_contract()

This is the control flow of the binary.

control_manipulation()

The main logic of this binary is it has read the 4 bytes from the user and have done xor to the system address and it is happening bitwise.

war_devils_prophecy()

And in this function the xor is done for the next remainig 4 bytes of the system address with the user input.

bomb_devils_contract()

This function has done the same thing but encoded the user input using the xor and the key is the system address.

Finding the vulnerability

The vulnerability exist here is buffer overflow since our size of the buffer is the 76 and the the data copied into it is 0x200 bytes.

Solving way

As we know the address of the binary during the runtime is in the little Indianans format which means if my data is 0xdeadbeef in the runtime it is:

\xef\xbe\xad\xde

This is for the 64 bit architecture.

So what we can do to exploit this binary is:

Step-1 :leak the low 4 bytes of the system address from the first function call 
step-2: leak the high 4 bytes of the system address form the second function call 
step-3: combine the both low+high bytes and unpack it to high indianess
step-4: Find the libc base and create your rop chain

dynamic analysis of the binary

This is how it is leaking the system address and the at the end since i have not given any input the ret is overwritten with the system address. Since

system_address^0=system_address

Finding the offset

Finding the offset is easy peasy just disassemble the function and look for the sub instruction at the top because it is pushing the rsp from the 0x50 down this is how stack is defined since rsp always points to the top of the stack.

So, our offset is:

0x50+8=88

Here, offset means the distance from the buffer to the RIP.

Crafting the payload 

offset+ROP_chain

ROP chain

If you don’t understand what is rop chain you can read my blog:

https://12bijaya.github.io/portfolio/blog/rop.html

But for this binary we will create rop chain like this since the vulnerability is buffer overflow.

rop = ret+pop_rdi;ret+[/bin/sh]+system

Which will give us the shell.

Payload 

payload = (b'A'*88 + rop_chain)^system

Since, our input is done xor with the system_address by the binary itself we also have to do xor to neutralize our payload
